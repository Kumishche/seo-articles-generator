# План бэкенда SEO Article AI (упрощенная версия)

API описан в [docs/openapi.yaml](docs/openapi.yaml).

## Границы версии

Входит: ввод темы и источников, анализ выдачи, структура, генерация, редактирование, AI-правка абзацев, повторная генерация, экспорт в HTML / Markdown / TXT, список статей.

Не входит (по сравнению с архитектурой из документов): PostgreSQL, MinIO, очереди, публикация в CMS, подключенные сайты, пользователи и аутентификация. Все хранится в памяти процесса и теряется при перезапуске. Хранилище спрятано за интерфейсами репозиториев, чтобы потом заменить его на JPA и MinIO без правок сервисов.

## Стек

- Java 21+ (собирается и запускается на JDK 25), Spring Boot 4.0 (ветка 3.5 уже вне поддержки), Maven (с `mvnw`, отдельно ставить Maven не нужно)
- `spring-boot-starter-webmvc`, `spring-boot-starter-validation`
- `com.openai:openai-java`: Responses API, structured outputs, встроенный инструмент `web_search`
- Jsoup: загрузка и разбор страниц конкурентов и ссылок пользователя
- Apache PDFBox и Apache POI: извлечение текста из PDF и DOCX
- springdoc-openapi: Swagger UI по адресу `/swagger-ui.html`, показывает контракт `docs/openapi.yaml`
- JUnit 5 и MockMvc; OpenAI в тестах подменяется заглушкой

Конфигурация через переменные окружения: `OPENAI_API_KEY`, `OPENAI_MODEL` (по умолчанию `gpt-5-mini`), `OPENAI_SEARCH_MODEL`, `OPENAI_BASE_URL` (прокси-шлюз), `CORS_ORIGINS` (по умолчанию `http://localhost:3000`).

## Сценарий работы (как во фронтенде)

1. **Экран «Новая статья».** Каждый файл сразу уходит в `POST /files`: сервер извлекает текст и возвращает `ArticleSource`. По кнопке «Начать анализ» вызывается `POST /articles` с темой, требованиями, планом и источниками. Ответ `202 {id}`, статус статьи `analyzing`.
2. **Анализ** (`@Async`, 5 этапов, совпадают с `analysisStages` во фронтенде):
   0. *Анализируем поисковую выдачу:* запрос к OpenAI с `web_search`, получаем 8-12 релевантных URL с заголовками.
   1. *Изучаем страницы конкурентов:* Jsoup загружает страницы (таймаут, лимит размера) и вытаскивает H1-H3 и основной текст. Сюда же добавляются ссылки и файлы пользователя.
   2. *Определяем поисковый интент* и 3. *Подбираем ключевые запросы:* один LLM-вызов со structured output возвращает интент, запросы, релевантность конкурентов и рекомендации.
   4. *Формируем структуру статьи:* LLM-вызов строит H1/H2/H3 с учетом выдачи, плана пользователя и рекомендаций, плюс оценку объема.

   Фронтенд опрашивает `GET /articles/{id}/research` и показывает `progress`. При ошибке `status = failed`, текст ошибки в `error`, статья возвращается в `draft`. Повторный запуск: `POST /articles/{id}/research`.
3. **Экран «Анализ и структура».** «Сохранить черновик» вызывает `PUT /outline`. «Сгенерировать статью» вызывает `POST /generate` со структурой; запрос синхронный и обычно идет 30-90 секунд.
4. **Генерация** в два прохода:
   - *Черновик:* LLM пишет HTML строго по структуре на материале конкурентов и источников пользователя, а также возвращает seoTitle, metaDescription и id использованных источников.
   - *Редактура:* второй проход сверяет текст с источниками, убирает шаблонные обороты из стоп-листа и выравнивает ритм (требование 6), не меняя структуру и ключевые запросы.

   После генерации HTML очищается по белому списку тегов (Jsoup Safelist), считаются slug и SEO-анализ, статус становится `review`.
5. **Экран «Редактор».** Автосохранение через `PUT /articles/{id}`, сервер пересчитывает SEO. AI-правка абзаца идет через `POST /paragraph-actions`, повторная генерация через `POST /regenerate`.
6. **Экспорт.** Диалог публикации оставляем только в режиме экспорта, файл отдает `GET /articles/{id}/export?format=…`.

## SEO-анализ

Проверки детерминированные, без LLM. Их id совпадают с теми, на которые завязан фронтенд: `intent`, `kw-title`, `kw-intro`, `density`, `length`, `headings`, `meta`, `links`. Только проверка `intent` берется из самооценки модели на шаге генерации. Оценка считается как взвешенная сумма проверок по шкале 0-100, вердикт: «Отлично» от 95, «Хорошо» от 75, «Удовлетворительно» от 50, ниже «Требует доработки». Целевое число упоминаний ключа (`KeywordStat.target`) зависит от объема статьи и типа ключа.

## Этапы реализации

1. Каркас проекта: pom, конфигурация, CORS, обработка ошибок, Swagger UI, in-memory репозитории.
2. Файлы и источники: `POST/DELETE /files`, извлечение текста из PDF/DOCX/TXT, загрузка ссылок.
3. Статьи: create, get, list, put, delete; машина статусов; slug.
4. Анализ: SearchClient на OpenAI web_search, разбор страниц, структурированные LLM-вызовы, прогресс, restart.
5. Генерация: промпты, два прохода, очистка HTML, regenerate, paragraph-actions.
6. SEO-анализатор и экспорт.
7. Тесты: контроллеры через MockMvc с заглушкой OpenAI, юнит-тесты SeoAnalyzer, Slugifier и экспорта.
8. README: запуск, переменные окружения, примеры curl.

Отдельный, девятый этап (по согласованию): подключение фронтенда. Нужно заменить моки в `lib/api.ts` на `request()`, добавить загрузку файлов с реальным прогрессом, заменить `articles/demo/*` на `articles/[id]/*`, сделать опрос статуса анализа, перевести AI-правку на API, убрать режим «на сайт» из диалога публикации.

## Риски

- **Долгая синхронная генерация.** Нужен таймаут HTTP-клиента OpenAI не меньше 3 минут; во фронтенде у `fetch` по умолчанию таймаута нет. Если окажется слишком долго, генерацию можно перевести на тот же асинхронный механизм, что и анализ.
- **Часть сайтов конкурентов блокирует Jsoup.** Такие страницы пропускаем, анализ продолжается по заголовку и сниппету из поиска.
- **Нет JDK.** На машине не найден JDK, для сборки нужен JDK 21.
